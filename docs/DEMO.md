# Slander local demo

The public site deploys automatically from **main** through `.github/workflows/public-demo.yml`, after domain tests and a public production build. Its source link points to main. GitHub Pages uses Actions deployments; the `gh-pages` branch archives generated assets so older open tabs keep working. A manual workflow run on main republishes the current source without resetting any visitor's browser records.

Publishing also requires desktop and mobile hover checks for The Girl in the Middle. These verify natural five-second looping, muted playback, reset on exit, current daily/weekly leaders, past daily/weekly winners, Admin and owner creatives and review dialogs, creator current/past ads and dialogs, and earnings/win cards before and after archiving. Mouse-only events and recovery after an interrupted play request are covered too. Set `PUBLIC_DEMO_BASE_URL=https://cooper2rich.github.io/slander/` when running the same Playwright checks against the live site; this skips the local preview server. Each test uses an isolated browser context, so fixture changes never alter a visitor's saved demo.

Public visitors can open the [GitHub Pages demo](https://cooper2rich.github.io/slander/) without signing in. The home page explains Blue Ripple Media’s mission and how to participate, with this week’s provisional campaign leaders and last week’s saved campaign winners. Home-page videos preview muted when at least half visible and pause offscreen or when the tab is hidden; Pause previews disables automatic playback. Both showcases use the existing campaign rankings and frozen history. Discover ads supports muted hover/keyboard previews, ad profiles with playable video, search/cause filters, illustrative impressions/CTR/cause donations, and a per-ad **Fund ad spend** action. The coffee collection uses real filmed footage throughout; original photo creatives appear as images. New eligible ads show N/A for unconnected metrics. Only eligible ads in active campaigns enter public discovery; private eligibility evidence and history are excluded.

Video previews loop the first five seconds while the pointer is over the ad and stop when it leaves. The shared player supports pointer and traditional mouse events and can retry an interrupted play request on subsequent movement. The Girl in the Middle previews in public cards/profiles, current and past leaderboards, Admin/owner creatives, creator ads, and the creator's earnings and win cards. Explicit Play retains full-length playback with sound; reduced-motion preferences continue to suppress automatic previews.

**Public-demo UX experiment, not a PRD amendment:** a separate browser-local viewer profile supports simulated ad-fund contributions and giving history. Registration creates only a `viewer` profile. It never creates a creator, campaign owner, or admin identity. No external authentication, email verification, or payments occur. New ad-fund contributions record a 10% creator / 5% application-use / 85% nonprofit allocation, rounded per contribution in integer cents. Historical contributions are retained without retroactively applying that split. Public support copy states the creator's 10% share. Ad funds remain separate from legacy cause gifts, votes and campaign seed/media pools. Allocations are not completed payouts, and actual purchases and payouts remain $0.

Only Admin can browse internal **Campaigns**. Admin opens a campaign to see its projects, creatives, ad spending and archived projects in a scoped sidebar. The main Admin archive holds archived campaigns. Campaign Owners see their own projects, spending, creatives, archived projects and activity; **Project requests** lets them propose a project without choosing or viewing an internal campaign. Admin assigns each approved request to a campaign belonging to that organization and creates one draft project. Requests and approvals are replay-safe. Setup pricing is pending; new drafts cannot publish or create a charge. Archiving a campaign archives its child projects and removes their ads from discovery; restoring it restores each child's previous status and retains funds and history.

Admin **Funding** ranks campaigns by daily sample growth, saved ad funds, nonprofit allocation or application fees. Each campaign and the application-fee summary distinguish 5% fees accrued, paid to the application and outstanding. Fictional sample application payments populate this view by default; saved visitor contributions have no completed transfers. Growth compares today's sample cause funds with yesterday in UTC. Missing evidence stays N/A. Actual saved ad-fund allocations, historical unallocated contributions and fictional sample payments are shown separately. Creator navigation is **My ads**, **Past ads**, **Earnings** and **Projects**; private creative history stays scoped to its creator.

Creator **Earnings** uses a creator-scoped projection of saved contribution allocations and completed attributed cause-gift commission records. It shows total earned, awaiting payout, paid to you and ad-fund earnings by ad, with ad-name search. The My ads summary links to Earnings and each ad displays its recorded commission. Withdrawn, archived and unavailable ads retain their saved earnings. Donor identities and other creators' contributions are excluded. Missing or unsupported historical allocations are disclosed and excluded from earnings rather than estimated from public sample performance. Real payouts remain unavailable. The normal local backend remains unchanged.

**Sample financial activity** is a separate, frozen browser-workspace fixture installed once without modifying viewer profiles, saved contributions, creative revisions or historical cause gifts. Existing demo creators have example ad-fund earnings and partially or fully paid commissions, and Admin sees 5% fees accrued, paid and outstanding per campaign plus a sample application payment history. Nocturne Studio: $1,040 earned / $600 paid / $440 pending. Nocturne campaign: $520 fees / $340 paid / $180 outstanding. Creator projections include only their own sample payouts. **Include sample activity** defaults on and can be disabled across My ads, Earnings and Admin Funding to show saved contributions alone. No samples enter viewer giving history, public donation metrics, leaderboard rankings, seed funds, the cause-gift ledger or real payment systems.

Creator **Earnings → Past leaderboard wins** shows compact daily and weekly cards alongside the earnings summary. Choose a completed period to see that creator's winning ad, campaign, impressions, total link clicks, funding and score, or follow **View result** to the public snapshot. The cards use the same frozen public results and creator IDs, including retained wins for ads that leave discovery. Only recent periods available in the public dropdowns are shown. Yakira has seven sample daily wins and four weekly wins. **Include sample activity** also controls these fictional wins; wins never increase earnings or create payouts.

The public demo retains project/detail settings, creator profiles, sample/uploaded submissions, automatic eligibility and revisions, scoped holds/appeals, activity, creator project terms and tracked giving. Existing cause-gift funding/performance and sample statement export remain available to Admin under the relevant campaign's **Cause-gift records**. They retain their historical accounting policy, separately from new ad funds. Project, creative, scope and exception behavior reuse the local domain modules, with actual browser SHA-256 and bundled-sample adapters. Browser-local media is stored in IndexedDB and persists across reloads. Public financial reports remain simulated browser illustrations; they do not create a server journal or payments. The public build never publishes the user's actual local workspace or files. Local backend workflows and the PRD are unchanged.

The public adapter initializes fictional seed projects and the Riverkind showcase once per browser. Earlier campaign-preview gifts and consent remain in browser storage and its sample creative is migrated into the full workspace. Role/profile selection persists across public-demo reloads. Demo selection illustrates scope, not authentication. Browser media and records are separate for each visitor. `tests/public-browser` covers both full project/upload/revision/hold/appeal/handoff flows and campaign/giving/report/export flows on desktop/mobile, with no `/api` network requests.

The current scope follows the user's instruction: this is a demo and not every aspect needs to function. The working core journey is discovery → frozen terms/consent → sample creative → automatic eligibility → tracked local gift → reports → exportable current sample week preview. ## Explicit fictional setup

Admin action: `POST /api/demo/showcase` with `x-demo-role: admin` and `{}`. It appends stable IDs under `fictional-river-showcase-v1`. A second call returns `created:false` and does not add funding again. It never deletes or replaces existing projects, posts, identities or media. All initialized identities and funding are fictional. Showcase terms are active from seven days before setup until ninety days after setup; initialize a new designed scenario if demonstrating after that offer has ended rather than resetting historical records.

`GET /api/demo/showcase` returns readiness and IDs. Creator shortcut `POST /api/campaigns/:id/sample-creative` uses approved sample bytes, shared submission/snapshot/evaluation and selected identity. Consent is recorded through normal `/consent`; the sample shortcut does not manufacture participation. `POST /api/campaigns/:id/demo-link` uses shared distribution/link operations and enforces creator ownership. `/r/:token` must be visited through an ordinary anchor so Express records the click before redirecting to public giving.

`POST /api/demo/sample-statement` is Admin-only and limited to the fictional campaign. It defines an exact current seven-day UTC sample period and returns the shared creator statement with a disclosure. This is an exportable preview, not a backdated/closed settlement or a future-clock payout simulation.

The browser keeps the legacy internal `nonprofit` option for compatibility and stores/maps it to `owner`; API requests use `x-demo-role: owner` plus `x-demo-organization`. Legacy nonprofit headers remain a compatibility alias server-side. Original records keep stable IDs.

## Existing domain APIs and deliberate limits

The accepted backend includes explicit organization ownership/beneficiaries, frozen offers, consent, distribution gates, source evidence/replay handling, balanced integer-cent journal, bounded restricted reservations/spend, finite seed promises/app-use, weekly manifests and simulated results, economics and evidence/configuration-gated grading. Their regression suites remain part of `npm run check`. The demo UI does not expose exhaustive forms for every API operation.

No live effects are available: no donation collection, payment-provider credentials, payouts, social OAuth/posting, ad buying, or verified external metrics. The UI honestly disables live controls. Fair initial exposure scheduling is a local API preview; comprehensive opportunity verification and advanced configuration UI are deferred. An illustrative score cannot pay a bonus or buy advertising. The 77.5 sample is not presented as observed campaign performance or causal impact.

The earlier approved-post-count leaderboard is an eligibility-count feature, not the performance grade. Other creators' private evidence/history is excluded from public projections. The public giving projection includes only campaign presentation fields.

## Architecture and checks

### Campaign ad platform setup

In the public working demo, choose Admin, then **Campaigns → a campaign → Ad platforms**. Every campaign card also has an Ad platforms shortcut, and the campaign Ad spending page links to the setup. Owners and creators cannot access or mutate these settings. Archived campaigns retain readable connections and previews; restoring them does not re-enable automation.

Allocation settings can also be edited directly on the campaign overview by expanding **Set ad spend allocation**. It reuses the same form, validation, per-campaign settings and preview operations as Ad platforms. Paused allocation rules can be saved before connecting accounts; enabling still requires the relevant demo destinations. Archived campaigns disable these controls.

**Campaign budget breakdown** is visible on the campaign overview, Ad platforms and campaign-scoped Ad spending. The saved campaign cap is split using the configured Meta percentage, with the remaining cents assigned to TikTok. Each platform shows Allocated, Spent and Left, plus a usage meter. Total left and platform left use signed integer cents (`allocated − spent`), so overruns remain negative and visible rather than being hidden. Changing and saving allocation updates the overview immediately; refresh and navigation use the same saved rules. Completed sample spending is included only when Include sample activity is enabled. Hiding it produces zero included spending and the full configured budget remaining, with an explicit samples-excluded label. No provider balance is implied.

Previews are now limited to nonnegative overall budget left and each platform's available remainder. Unused shares stay unallocated; amounts are not automatically transferred to cover another platform's overrun. When the total budget is exhausted, a preview has no planned spending and explains why. Previews store whether sample history was included; switching visibility requires a fresh preview so the displayed plan cannot contradict the breakdown. Running a preview still creates no charge, reservation or actual-spend record, and never consumes the budget by itself.

**Ad budget breakdown** adds an entry for every campaign ad, with total and Meta/TikTok Allocated, Spent and Left figures. Each platform's full campaign allocation is divided equally in integer cents among its currently eligible ads, with stable ad-ID ordering for cent remainders. These are calculated shares, not independent per-ad settings. TikTok and Meta video-view destinations require video; draft, held, withdrawn, stale or inactive creatives receive zero new allocation. A platform without eligible creatives retains an explicit unassigned allocation. Per-ad rows plus unassigned allocation equal the campaign's totals for allocated and remaining cents.

Completed examples now carry stable ad IDs rather than relying on titles to associate spend. Renaming an ad cannot lose its history or attach spending to another ad with the same title. Historical ads without a current creative remain visible with zero new allocation and any negative remaining balance. Sample visibility applies consistently to campaign and ad figures. Allocation previews also cap each ad at its nonnegative remaining amount; capped shares are redistributed fairly among other eligible ads on the same platform until the available daily amount or all ad limits are exhausted. No cross-platform transfers, live orders or financial mutations are introduced.

Campaign overviews, Ad spending pages and Ad platforms now show **Completed ad spend**. Fixed October 21–23, 2026 examples total $700 for Coffee ($420 Meta / $280 TikTok), $2,000 for River ($1,250 Meta / $750 TikTok), and $1,500 for Adoption ($900 Meta / $600 TikTok). Rows retain a creative label, date, platform, amount and Completed · sample status. Reports filter by the visible project IDs, so owners see their own organizations' examples and new campaigns start empty. Repeated visits do not append or duplicate records; archived projects retain their history. Include sample activity controls visibility across these pages and persists on refresh. These are presentation fixtures separate from contributor, payout, platform-spend and allocation-planning records. They do not change saved caps, fabricate live provider evidence, alter creator earnings or move money. When included, their amounts reduce budget remaining and constrain allocation previews.

The connection dialogs select fictional Meta or TikTok USD ad accounts and a traffic or video-view target belonging to the BRM campaign. No real credentials or access tokens are requested or stored. Configure the daily limit and campaign cap in USD, set the Meta percentage (TikTok receives the remainder), enable demo automation and save. A platform receiving a nonzero share must have a selected destination. Daily limits cannot exceed the campaign cap. Changing or disconnecting an account pauses automation and invalidates the previous preview.

**Preview next allocation** uses the saved rules, current campaign/project state and existing deterministic creative eligibility. Meta traffic targets support eligible images and videos; TikTok and video-view targets use eligible videos. The budget is split in integer cents, then equally among eligible creatives on each platform with deterministic remainder allocation. Draft, inactive, expired, held, withdrawn, stale-snapshot and other-campaign creatives are excluded. Shares without usable creatives remain unallocated. The latest preview persists with its timestamp, selected destinations and individual allocations.

This is a browser-local planning preview. Its campaign cap is a configured limit, not a verified balance. Repeated previews do not consume a cumulative budget, place platform orders, mutate contributor allocations, manufacture spend or alter earnings. Actual platform spend stays $0. There is no timer or background runner. Tests cover role/campaign isolation, cent conservation, media eligibility, invalid settings, refresh persistence, disconnect and archive behavior on desktop and mobile.

A later live integration would need a deployed server for advertiser authorization callbacks and secret storage, access verification, external campaign/ad mapping, platform review, authenticated spending authorization, reservations, an idempotent worker, cumulative cap enforcement and spend reconciliation. Provider references: [Meta Marketing API](https://developers.facebook.com/docs/marketing-apis/), [TikTok authorization](https://business-api.tiktok.com/gateway/docs/index?doc_id=1738373141733378), and [TikTok Marketing API](https://business-api.tiktok.com/portal/docs/marketing-api/v2.0). The current UI provides a clearly labeled demo rather than initiating provider authorization.

`server/demo-showcase.js` composes existing domain operations for the explicit fictional scenario. `src/pages/Campaigns.tsx` provides discovery/details, funding/performance/statement tabs and the public giving screen. Existing pages remain in their established shell.

`tests/showcase.test.js` verifies append-only idempotence and original-record preservation, restricted pool amounts, consent → eligibility → tracked gift, cookie renewal, replay-safe confirmation, current-week statement, role scope, grade arithmetic and immediate public-media suspension. `tests/browser/marketplace.spec.ts` clicks the visible desktop/mobile core journey, confirms $10/$90/+1, checks scopes and downloads, checks overflow and records screenshots. Existing browser/unit/financial/analytics suites remain required.

All test state uses temporary or `test-results` SQLite directories. The user's `data/` is never a test fixture.
